I. Overview
1. User Requirements
1.1 Actors
#
Actor
Description
1
Customer
(Diner / Guest)
The end-user dining at the restaurant. They interact with the system via a mobile web browser by scanning the table's QR code. A customer joins or initiates an active Dining Session, browses the digital menu, manages the shopping cart, places food orders, tracks real-time order status (PENDING → SERVED), and submits service requests (calling staff, requesting bills).
2
Waiter
(Service Staff)
Front-of-house staff responsible for physical customer service. They monitor the table status map, assist guests with ordering or order adjustments if needed, receive notifications when dishes are marked as READY by the kitchen, deliver food to tables, and update order item status to SERVED. They also receive and attend to customer assistance calls.
3
Kitchen Staff
(Cook / Chef)
Back-of-house staff operating the Kitchen Display System (KDS). They receive incoming orders, acknowledge and accept orders, update preparation states (CONFIRMED → PREPARING → READY), or reject items (REJECTED) in case ingredients are out of stock.
4
Cashier
Front-of-house staff handling billing and settlement. They access active dining sessions, consolidate all placed orders into a single final bill, apply discounts (if applicable), process payments (cash or QR/bank transfer), confirm payment status, complete the Dining Session, and release the table to AVAILABLE.
5
Restaurant Manager
(Admin)
High-level administrator supervising restaurant operations. They manage staff accounts and role authorizations, configure restaurant tables and generate secured table QR codes, manage menu categories and food items (prices, images, availability), and review dashboard analytics (daily revenue, order volumes, popular items).
6
Payment Gateway
External System
An external software system (e.g., VNPay, Momo, or VietQR/Banking API) that interfaces with the system to process non-cash transactions, validating payment statuses and returning transaction callbacks/webhooks to the backend.

2.4 Non-UI Functions
#
Feature
System Function
Description
1
Security & QR
FN‑01: QR Token Generator & Verifier
Backend cryptographic utility that generates HMAC-SHA256 encrypted tamper-proof tokens embedding table identifiers and a server-side secret key during QR stand printing, and validates signature integrity upon customer scan (BR-04), completely preventing table identity spoofing.
2
Order Lifecycle
FN‑02: Order State Transition Validator
Central state machine validator engine: strictly enforces legitimate order item lifecycle transitions (PENDING → CONFIRMED → PREPARING → READY → SERVED), rejecting illegal state jumps and preventing customer self-cancellation once food preparation has commenced (BR-05, BR-06).
3
Order Routing
FN‑03: Beverage / Drink Bypass Router
Automated order routing rule engine: upon order placement, items flagged as pre-packaged beverages or bar items (is_drink = 1) bypass the kitchen cooking queue, are automatically set to READY, and dispatch a serving task directly to floor waiters (UC-31).
4
Concurrency
FN‑04: Idempotency Key & Dedup Service
Server-side request deduplication service: validates unique Idempotency-Key headers (UUID v4) attached to each place-order request within an active Dining Session, preventing accidental duplicate orders caused by double-clicking or intermittent mobile network retransmissions (BR-03).
5
Reservation
FN‑05: Scheduled Reservation Auto-Release
Background cron job executing every 5 minutes: scans upcoming table reservations; if current time exceeds reservation scheduled arrival by more than 20 minutes without customer check-in, automatically transitions the booking to EXPIRED and resets table status to AVAILABLE (BR-07).
6
Payment Gateway
FN‑06: Payment Webhook & IPN Listener
Asynchronous payment gateway notification webhook endpoint (VietQR / VNPay Sandbox): verifies digital transaction signatures, matches reference order codes and amounts, updates bill records to PAID, and signals automatic session completion.
7
Analytics
FN‑07: Daily Sales Metric Aggregator
Scheduled nightly aggregation worker executing at 00:05 daily: aggregates total net sales, dish volume counts, table turnover ratios, and void/cancellation losses; updates historical reporting data models to support rapid analytics dashboard queries (UC-28).

Stores physical restaurant table layouts, table numbers, seating capacities (2/4/6/8 pax), dining area zones (Floor 1, Floor 2, Outdoor), physical status (AVAILABLE, OCCUPIED, RESERVED, CLEANING), and HMAC-SHA256 encrypted QR secret signature.

- Foreign keys: None
04
dining_sessions
Core Hub Entity: Represents an active dining occupancy for a specific table. Created upon customer QR scan or staff assignment (ACTIVE), tracks start/end timestamps and party size, and is finalized upon payment settlement (CLOSED).
- Primary keys: id
- Foreign keys: table_id (references dining_tables.id), opened_by (references users.id, nullable)
05
categories
Stores food and beverage classification groupings (Starters, Main Courses, Hotpot/Grill, Desserts, Beverages) with display sequence and activation flags.
- Primary keys: id
- Foreign keys: None
06
food_items
Stores menu items including names, descriptions, base prices, image URLs, availability flags, and an is_drink indicator for automatic kitchen queue bypass.
- Primary keys: id
- Foreign keys: category_id (references categories.id)
07
orders
Represents an individual batch order submission within an active dining session. Multiple orders can belong to a single dining session. Tracks order timestamp, order type (CUSTOMER or WAITER_ASSISTED), and UUID idempotency key.
- Primary keys: id
- Foreign keys: session_id (references dining_sessions.id)
08
order_items
KDS State Machine Entity: Tracks individual ordered food items, quantity, snapshot unit price, customer special preparation notes, rejection reason, optimistic locking version, and lifecycle status (CONFIRMED → PREPARING → READY → SERVED, or REJECTED / CANCELLED).
- Primary keys: id
- Foreign keys: order_id (references orders.id), food_id (references food_items.id)
09
bills
Stores financial checkout transactions for a completed dining session: aggregates subtotal of all SERVED items, voucher discount amount, 8% VAT tax amount, final payable amount, payment method (CASH / VIETQR), payment status, and bank transaction reference.
- Primary keys: id
- Foreign keys: session_id (references dining_sessions.id, UNIQUE), cashier_id (references users.id)
10
reservations
Stores customer advance bookings: guest contact details, party size, scheduled arrival time, pre-assigned table, and status (PENDING, CONFIRMED, CHECKED_IN, EXPIRED, CANCELLED).
- Primary keys: id
- Foreign keys: table_id (references dining_tables.id, nullable)
11
audit_logs
Immutable audit log capturing sensitive operations: kitchen item rejections (REJECT_ITEM), waiter/manager item voids (VOID_ITEM), table transfers, and cancellations with mandatory reason notes and actor identification for loss prevention.
- Primary keys: id
- Foreign keys: performed_by (references users.id, nullable)

II. Requirement Specifications
1. Common Functions
1.1 UC-01_Login System (Staff RBAC Authentication)
a. Functional Description
UC ID and Name
UC-01_Login System
Created By
ROMS Development Team
Date Created
16/09/2026
Primary Actor
Restaurant Staff (Waiter, Kitchen Staff, Cashier, Manager)
Secondary Actors
System Security Service (JWT Provider, Rate Limiter)
Description
Authenticates internal staff credentials, verifies RBAC roles, and issues signed JWT tokens for role-based dashboard access.
Trigger
Staff member opens the internal portal and submits login credentials.
Preconditions
Staff account exists in SQL Server with status ACTIVE. Network is reachable.
Postconditions
JWT token stored securely; user redirected to assigned operational view (Table Map, KDS, POS, or Dashboard).
Normal Flow
1. User accesses staff login view (/staff/login).
2. System presents login form requesting Username/Email and Password.
3. User inputs valid credentials and taps "Sign In".
4. Backend validates input syntax and verifies BCrypt hash against database.
5. System checks account status is ACTIVE.
6. System generates signed JWT containing user_id and role claim.
7. System logs successful login into AuditLog.
8. System redirects user to their assigned portal based on role.

UPDATE reservations
SET status = 'EXPIRED', updated_at = NOW()
WHERE status = 'CONFIRMED'
  AND reservation_time < DATEADD(minute, -20, NOW());
IV. Appendix
Assumptions & Dependencies
1.1 Assumptions
ID
Assumption Title
Detailed Description
AS-01
Single Restaurant Scope
The system is designed, developed, and deployed exclusively for a single, independent restaurant premise. Multi-branch management, central chain administration, franchise hierarchies, and multi-tenant SaaS business models are explicitly outside the current project scope.
AS-02
Customer Device & Browser Access
Customers possess a personal smartphone equipped with a functioning camera capable of reading standard 2D QR codes and a modern mobile web browser (e.g., Apple Safari, Google Chrome) with network connectivity. Customers are not required to download or install a native mobile app.
AS-03
Restaurant Hardware Infrastructure
The restaurant facility is equipped with dedicated operating devices: a display tablet or PC monitor for the Kitchen Display System (KDS) in the culinary area, at least one Cashier/POS PC terminal at the counter, and handheld mobile devices or tablets for floor waitstaff.
AS-04
Cooperative Table Dining Session
Guests seated at the same physical dining table are assumed to belong to the same dining group, share a single active Dining Session, and accept a single consolidated bill upon checkout. Automated individual item split-billing is excluded from the MVP scope.
AS-05
Menu & Inventory Maintenance
Restaurant management and kitchen personnel are responsible for maintaining and updating menu item availability in real time. The system assumes that active catalog records accurately reflect actual culinary ingredient availability in the kitchen.
AS-06
Staff Operational Training
Floor waitstaff and kitchen personnel are trained on and strictly adhere to the defined Order State Machine lifecycle (CONFIRMED → PREPARING → READY → SERVED) and update order statuses promptly during operational service.
AS-07
Continuous Power & Facility Network
The restaurant facility provides continuous, uninterrupted electrical power and adequate local Wi-Fi coverage across all dining tables, cashier stations, and food preparation areas to ensure seamless device connectivity.

ID
Dependency Title
Detailed Description
DE-01
Network Connectivity
ROMS depends on a stable network connection for communication between customer devices, staff devices, frontend, backend, and database services.
DE-02
Electronic Payment Service
Electronic payment functionality depends on the availability of the selected payment service, currently specified as VNPay QR in the project scope. Cash payment remains available as an alternative.

Printed receipts depend on the availability of a compatible receipt printer. The core payment workflow should remain functional even when receipt printing is unavailable.
2. Limitations & Exclusions
2.1 Excluded Features
ID
Excluded Feature
Detailed Description
EX-01
Multi-Branch and Multi-Restaurant Operations
ROMS supports a single restaurant only. Multi-restaurant, multi-branch, multi-tenant, and franchise operations are outside the current project scope.
EX-02
Off-Premise Food Delivery
ROMS is designed for in-dining table ordering and does not support home delivery, delivery dispatch, driver management, takeaway logistics, or third-party food delivery platform integration.
EX-03
Native Mobile Applications
ROMS does not include dedicated native mobile applications for Android or iOS. Customer and staff interactions are provided through web-based interfaces.
EX-04
Individual Split Billing
ROMS does not support automated split billing between individual diners. Orders within the same Dining Session are aggregated into a single consolidated bill.
EX-05
Advanced Inventory and Ingredient Management
ROMS does not support advanced inventory management, including detailed ingredient/BOM tracking, raw material consumption, supplier management, or purchase order management. Food availability is managed at the menu-item level.
EX-06
Customer Loyalty Programs
ROMS does not support loyalty points, membership tiers, reward redemption, or customer loyalty campaigns.
EX-07
Advanced AI/ML Recommendation
ROMS does not include advanced AI/ML-based food recommendation or personalization. Any food recommendation functionality is limited to the basic/rule-based scope defined for the project.
2.2 Technical & Operational Limitations
ID
Limitation / Constraint
Detailed Description
LI-01
Network Dependency
ROMS operates as an online web-based system and does not provide offline operation. Loss of network connectivity may interrupt customer ordering, staff operations, and communication with kitchen services until connectivity is restored.
LI-02
No Online Reservation Deposit
ROMS does not support online deposits or advance payments for reservations. Reservation handling, when implemented, is limited to the table reservation and check-in functionality defined within the project scope.
3. Business Rules
ID
Category
Rule Definition
BR-01
Constraints
A table can have only one active Dining Session at a time.
BR-02
Facts
A Dining Session can include multiple Customers.
BR-03
Constraints
A Customer can participate in only one active Dining Session at a time.
BR-04
Constraints
An Order must contain at least one valid and available menu item.
BR-05
Constraints
A Customer can cancel an Order only before it reaches PREPARING.
BR-06
Constraints
An Order status can only be changed according to the predefined Order State Machine.
BR-07
Constraints
Only authorized Staff can change the Order status according to their assigned permissions.
BR-08
Constraints
A Dining Session can be completed only when all associated Orders have reached a final status.
BR-09
Computations
A Bill belongs to one Dining Session and is calculated from all valid payable Orders within that session.
BR-10
Constraints
Canceled and rejected Orders must not be included in the Bill.
BR-11
Constraints
A Customer can access a Dining Session only when the scanned QR code is valid and associated with an active table or Dining Session.
BR-12
Action Enablers
A recommended item must not be automatically added to the Customer's Cart. Customer confirmation is required before adding the item.
BR-13
Constraints
A table marked as RESERVED must not be assigned to walk-in customers during the active reservation period.
BR-14
Constraints
Each Order must strictly belong to exactly one valid Dining Session.
BR-15
Constraints
A Reservation can only be created for a future date and time. Reservation requests for past timestamps must be rejected by the backend with HTTP 400.
BR-16
Constraints
A Dining Session can only be transitioned to COMPLETED when no Order Items remain in intermediate states (PENDING, CONFIRMED, PREPARING, or READY) within that session. Checkout is blocked if any item is still being prepared.
BR-17
Computations
The price recorded on each Order Item is the snapshot unit price at the time the Order was placed (order_items.unit_price), not the current menu price. Subsequent price changes to a MenuItem do not retroactively affect existing Bills.
